## Persisted foundation

- Patient has a global UUID generated by Prisma, mandatory Clinic ownership, and a patientCode unique within that clinic. Phase 2 must generate canonical uppercase codes server-side and handle collisions without count-based numbering.
- Name, optional date of birth and contact fields support identity. Normalized name/phone/email columns and clinic-prefixed indexes support duplicate candidate searches; shared names or family contact details are deliberately not unique constraints. Phase 2 must normalize these fields consistently before writes.
- Optional clinicalNotes, medicalHistory and dentalHistory store only supplied information. Timestamps, revision and archivedAt support future guarded updates/archiving. These fields are not an append-only edit audit; authenticated transactional change history remains Phase 2 design/work.
- One Patient can have many PortalCases. The composite foreign key (clinicId, patientId) prevents linking another clinic's patient even if application code makes a mistake. Restrict delete/update actions prevent silent loss of links or transfer of linked patients between clinics.
- PortalCase.patientId is nullable. Existing patientReference remains required and unchanged. No automatic matching, backfill, seed or merging was performed. Existing case creation continues to work without patientId.

Run the transaction-only integrity test against the documented local database:

```powershell
node scripts/patient-integrity.cjs
```

It rejects other database hosts/ports, creates clearly synthetic fixtures inside one transaction, and always rolls them back. Checks: scoped code uniqueness, same code in different clinics, repeated names allowed, missing clinic rejection, multiple cases, legacy NULL links, cross-clinic/missing patient rejection, linked-patient deletion/transfer rejection, and clinic deletion restriction. Never adapt this into a production seeder.
